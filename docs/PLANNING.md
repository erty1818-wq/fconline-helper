# FC Online Helper — 기획안 v0.1

> 작성일: 2026-09-24
> 대상: 개인용 Windows 데스크톱 컴패니언 (FC온라인 1:1 공식경기)
> 원칙: **사람이 직접 검색하면 볼 수 있는 정보만** 쓴다. 게임 메모리 읽기, 인젝션, 패킷 가로채기, 입력 자동화는 하지 않는다.

## 0. 조사 방법과 검증 수준 (먼저 읽을 것)

이 문서의 API 관련 내용은 다음 자료로 확인했다.

| 자료 | 상태 |
|---|---|
| NEXON Open API 공식 문서 (openapi.nexon.com) | **작성 환경의 네트워크에서 접속이 차단돼 본문을 직접 열지 못함.** 검색 결과에 나온 제목과 요약만 확인 |
| `nexon-open-api` npm 패키지 v0.1.1 (2026-03 배포, 제3자 SDK) | 코드를 내려받아 FC온라인 엔드포인트와 응답 타입 정의를 직접 확인 |
| `nexon-openapi` PyPI 패키지 v0.0.9 (제3자 SDK) | 엔드포인트 경로를 교차 확인 |
| 공식 공지 "매치 정보 x, y 좌표 값 정보 안내", "매치 정보 관련 변환식 공지" | 검색 결과 요약으로 확인 (좌표 0~1, 1을 넘으면 경기장 밖) |

따라서 아래 표시를 붙인다.

- ✅ **확인됨**: 두 개 이상의 자료가 일치함
- ⚠️ **확인 필요**: 제3자 자료에만 있거나 추정이 들어간 내용. 개발을 시작하는 날 공식 문서에서 다시 확인할 것

**개발 1일 차 필수 작업**: API Key를 발급받은 뒤 내 계정으로 `match-detail`을 실제로 몇 건 호출해 원본 JSON을 `docs/samples/`에 저장한다. 이 문서의 필드 해석은 모두 그 실측 데이터로 다시 검증한다.

## 1. 이 프로그램의 목적 (재정의)

사용자가 적은 목적은 "상대 전적을 빠르게 보여주는 프로그램"에 가깝다. 하지만 전적검색은 FC.GG, 공식 데이터센터 같은 사이트가 이미 잘 하고 있다. 여기서 경쟁하면 이길 이유가 없다.

이 프로그램의 가치는 다음 한 문장으로 정의하는 게 맞다.

> **"킥오프 전 몇 초 안에, 이 상대에 대해 알아야 할 3가지와 내가 기억해야 할 것을 클릭 없이 보여주는 개인 비서."**

여기서 핵심은 네 가지다.

1. **클릭 없이**: 검색창에 닉네임을 치는 순간 이미 늦다. 자동 인식이 핵심 경험이다 (단, MVP는 수동 입력으로 시작).
2. **3가지**: 지표 40개가 아니라, 이 상대가 평균적인 유저와 **다른 점**만 보여준다.
3. **약점까지**: 상대가 어떻게 넣는지뿐 아니라 **어떻게 먹히는지**도 보여준다. 대부분의 전적 사이트가 놓치는 부분이다.
4. **내가 기억해야 할 것**: 재대결 여부, 지난번 결과, 내가 남긴 메모. 웹사이트는 "나"를 모른다. 로컬 프로그램만 할 수 있는 영역이다.

## 2. 기술적 가능성 평가

| 영역 | 판단 | 근거 |
|---|---|---|
| 닉네임 → 상대 최근 경기 분석 | **가능** ✅ | `id` → `user/match` → `match-detail` 순서로 조회 |
| 득점 방식·위치 분석 | **가능** ✅ | `shootDetail`에 슈팅마다 좌표, 종류, 결과, 선수, 도움 선수, 도움 좌표가 있음 |
| 패스·수비 성향 | **부분 가능** | 경기 단위 합계만 있음. 패스 위치는 없음 |
| 현재 등급 | **부분 가능** | `user/maxdivision`은 역대 최고 등급. 대신 `match-detail`의 `matchInfo.division`이 **그 경기 시점의 등급**이라, 최근 경기 기준 등급은 보여줄 수 있다 (3.4 실측). 실시간 등급은 OCR로만 가능 |
| 포메이션 | **추정만 가능** | 포메이션 필드가 없음. 선발 선수의 `spPosition` 조합으로 추정 |
| 키보드/패드 | **가능** ✅ | `matchDetail.controller` 필드 존재 |
| 자동 상대 인식 (OCR) | **가능, 조건부** | 게임을 **테두리 없는 창 모드**로 실행해야 캡처와 오버레이가 안정적임 |
| 경기 시작·종료 자동 감지 | **어려움** | 메모리를 읽지 않으면 확실한 신호가 없음. 단축키 + 화면 신호 + API 사후 확인 조합으로 해결 (20장) |
| 경기 중 실시간 정보 | **의미 없음** | API는 경기가 **끝난 뒤** 기록을 줌. 경기 중 새로 알 수 있는 정보가 없음 |
| 음악 플레이어 | **가능, 가볍게** | Windows 내장 미디어 API로 추가 라이브러리 거의 없이 구현 |

**결론**: 핵심 기능은 모두 공식 API만으로 만들 수 있다. 어려운 부분은 "언제 조회를 시작할지"(자동 인식)와 "몇 초 안에 결과를 띄울지"(호출량·캐시)다. 기능 구현이 어려운 게 아니라 **타이밍 설계**가 어렵다.

## 3. FC온라인 Open API 활용 가능 데이터

기본 URL: `https://open.api.nexon.com/fconline/v1/` · 인증 헤더: `x-nxopen-api-key` ✅

### 3.1 엔드포인트

| 경로 | 용도 | 비고 |
|---|---|---|
| `GET id?nickname=` | 닉네임 → `ouid` | ✅ `ouid`는 닉네임이 바뀌어도 유지되는 식별자. **로컬 DB의 기본 키로 사용** |
| `GET user/basic?ouid=` | 닉네임, 레벨 | ✅ |
| `GET user/maxdivision?ouid=` | 매치 종류별 **역대 최고 등급**과 달성일 | ✅ 현재 등급 아님 |
| `GET user/match?ouid=&matchtype=&offset=&limit=` | 매치 ID 목록 | ✅ `limit` 최대 100 |
| `GET match-detail?matchid=` | 경기 상세 (**양쪽 유저 모두**) | ✅ 핵심 데이터 |
| `GET user/trade?ouid=&tradetype=buy\|sell` | 이적시장 거래 기록 | 내 계정용으로만 쓰는 것을 권장 |
| `GET match?matchtype=&orderby=` | 전체 유저의 최근 매치 ID 목록 | ⚠️ 메타(유행) 분석용 표본 수집에 활용 가능 |
| `POST ranker-stats` (matchtype, players[]) | 랭커가 쓴 선수의 20경기 평균 스탯 | ⚠️ 한 번에 50명 이하 권장. "평균 대비" 기준선으로 활용 |
| `static/fconline/meta/{matchtype,spid,seasonid,spposition,division,division-volta}.json` | 메타데이터 | ✅ 인증 불필요. `spid`는 용량이 큼 → SQLite에 한 번만 적재. 볼타 등급은 `division-volta`(하이픈). `division_volta`는 403 |
| `live/externalAssets/common/players/p{spid}.png` | 선수 이미지 | 디스크 캐시 |

`matchtype` 코드는 하드코딩하지 말고 `meta/matchtype.json`에서 불러온다 (공식경기 = 50으로 알려져 있으나 ⚠️).

### 3.2 `match-detail` 안에 들어 있는 것 (유저별 `matchInfo[]`)

- **matchDetail**: 승/무/패, 종료 타입(0 정상, **1 몰수승, 2 몰수패**), **일시정지 횟수**, 파울, 부상, 카드, 드리블 거리, 코너킥, 점유율, 오프사이드, 평균 평점, **컨트롤러 종류**
- **shoot**: 전체/유효 슈팅, 헤더·프리킥·박스 안·박스 밖·PK 슈팅/골, 자책골, 승부차기
- **shootDetail[]** (슈팅 1개당 1건):
  - `goalTime`: 인코딩된 시각. `2^24` 단위로 전반/후반/연장/승부차기를 구분
  - `x`, `y`: 0~1로 정규화한 좌표
  - `type`: 1 일반, 2 감아차기, 3 헤더, 4 로빙, 5 플레어, 6 낮은 슛, 7 발리, 8 프리킥, 9 PK, 10 무회전, 11 바이시클, 12 파워샷 ⚠️
  - `result`: 1 유효, 2 빗나감, 3 골
  - `spId`, `spGrade`(강화), `spLevel`
  - `assist`, `assistSpId`, `assistX`, `assistY` (도움 선수와 도움 위치)
  - `hitPost`, `inPenalty`
- **pass**: 전체·숏·롱·바운싱 로브·드리븐 땅볼·스루·로빙 스루 패스의 시도/성공 (합계만)
- **defence**: 블락·태클 시도/성공
- **player[]**: 선수별 `spId`, `spPosition`, `spGrade`, 그리고 슈팅·골·도움·드리블·인터셉트·패스·공중볼·태클·블락·카드·평점

### 3.3 API에 없는 것 (중요)

- **현재 등급**, 랭킹 점수 변동
- **포메이션, 팀 전술, 개인 전술**
- **패스·드리블·태클의 위치** (좌표는 슈팅과 도움에만 있음)
- 이벤트 타임라인 (슈팅 외 시각 정보 없음)
- 선수 **가격**, 팀컬러, 구단 가치
- 상대 **플레이 스킬** (개인기, 컷백, 얼리크로스 등 조작 종류)

### 3.4 확인 필요 항목 — 실측 결과 (2026-09-25)

실제 응답 34경기(슈팅 428개, 골 177개)와 공식 문서의 `MatchDetail` 스키마로 검증했다. 원본은 `docs/samples/*.local.json`(git 제외).
테스트 `Local_real_samples_parse_and_match_the_verified_semantics`가 로컬 원본이 있으면 아래 내용을 매번 다시 확인한다.

| 항목 | 결과 |
|---|---|
| 좌표 x 방향 | ✅ **양 팀 모두 자기가 공격하는 골대가 x = 1**로 정규화돼 있다. 골 177개 전부 x 0.75~0.99. `inPenalty`는 x ≥ 1 − 16.5/105(0.843)에서 정확히 바뀐다 (슈팅 428개 전부 일치) |
| 좌표 y 방향 | ✅ **y가 작을수록 공격 방향 기준 왼쪽.** 왼쪽 풀백·윙어의 도움 평균 y = 0.20, 오른쪽 0.78 |
| `shootDetail.type` | ✅ 공식 스키마의 1~12 목록이 3.2와 같다 (12 = super, 파워샷). 헤더(3)·프리킥(8)·PK(9)는 `shoot` 합계와도 일치. ⚠️ **실제 데이터에 13, 14가 나오지만 공식 목록에 없다.** 13은 거의 전부 박스 밖 17~45m 슈팅. 의미를 확인할 때까지 "기타"로 표시 |
| 도움 선수 필드 | 실제 응답은 **`assistSpId`**, 공식 스키마는 `assistSpI`. 둘 다 받는다. 같은 식으로 `ballPossesionSuc`(문서) / **`ballPossesionSuccess`**(실제) |
| `goalTotal` vs `goalTotalDisplay` | `goalTotal` = 자기 슈팅으로 넣은 골 (= `shootDetail`의 골 수). `goalTotalDisplay` = 경기 후 표시 점수: **상대 자책골 포함, 몰수 시 3:0**. 자책골에는 슈팅 기록이 없다 |
| `shoot` 합계 | `shootHeading`, `shootInPenalty` 등은 `shootDetail`보다 조금 적게 세는 경우가 있다. 분석은 `shootDetail`을 기준으로 한다 |
| 공식경기 matchtype | ✅ 50 (`meta/matchtype.json`). 메타데이터는 키 없이 받아진다 |
| `matchDate` | 공식 스키마상 **UTC** (오프셋 없이 옴) |
| 컨트롤러 | 문서는 `pad`, 실제는 **`gamepad`**. 몰수패 쪽은 빈 값 |
| `matchInfo.division` | **그 경기 시점의 등급.** 최고 등급(`maxdivision`)과 다르게 경기마다 바뀐다 → 2장의 "현재 등급 API로 불가"를 수정: 최근 경기의 등급으로 대신 보여줄 수 있다 |
| 몰수패 쪽 기록 | 경기 전에 나간 쪽은 **모든 숫자가 `null`, `player`가 빈 배열**로 온다. 전적·탈주율에는 넣고 스타일 평균에서는 뺀다 |
| 에러 응답 | 잘못된 키는 401이 아니라 **400 `OPENAPI00005`**, 없는 닉네임은 400 `OPENAPI00004`. 에러 이름으로 구분해야 한다 |
| 데이터 반영 | 공식 안내: "데이터는 매시 정각, 두 시간 전의 게임 데이터가 업데이트". 경기 직후 리포트(8.3)는 1~3시간 늦을 수 있다 ⚠️ 실측 필요 |

아직 확인하지 못한 것 ⚠️

- **개발 단계 Key의 호출 한도**: 응답 헤더와 가이드 문서에 숫자가 없다. 앱 상세의 통계정보에서 확인한다. 그때까지 초당 5회 (설정 가능).
- `type` 13, 14의 의미 (새로 추가된 슈팅 종류로 추정)
- **조회 가능한 과거 기간**: 어떤 유저는 공식경기가 14경기만 조회됐다
- `user/trade`를 다른 유저의 `ouid`로 조회할 수 있는지, 조회해도 되는지

실측으로 새로 드러난 제약

- **30일 갱신 의무**: API 페이지 고지 "API를 통해 데이터를 크롤링한 경우 30일 이내에 크롤링한 데이터를 갱신해야 할 의무". 17.4의 "매치 상세 영구 캐시"와 충돌한다. 30일이 지난 원본은 다시 받거나 지우는 정책이 필요하다 (미구현).
- **ouid 변경 가능**: 공식 안내 "게임 콘텐츠 변경으로 ouid가 변경될 수 있습니다". ouid를 영구 키로 쓰는 설계(3.1, 17.3)에 닉네임 기반 재연결이 필요할 수 있다.

| 키보드/패드 | O [직접] | `controller` |

## 5. 어렵거나 불가능한 기능, 그리고 반론

**불가능하거나 권하지 않는 것**

1. **현재 등급을 API로 가져오기**: 불가능하다. 최고 등급을 "현재 등급"처럼 보여주면 틀린 정보가 된다. UI에 반드시 "최고 등급"이라고 적는다.
2. **"컷백 플레이어", "개인기 장인" 같은 단정**: 조작 정보가 없다. [추정] 표시와 근거를 함께 보여줄 때만 쓴다.
3. **경기 중 오버레이**: 경기 중에는 API에 새 정보가 없다. 화면을 가리기만 한다. **넣지 않는 것을 권한다.** 단축키를 누르고 있는 동안만 보이는 "살짝 보기" 정도면 충분하다.
4. **FC.GG 등 전적 사이트 스크래핑**: 그 사이트들도 같은 공식 API를 쓴다. 긁어 올 이유가 없고, 해당 사이트 약관 위반과 차단 위험만 생긴다. **전적은 공식 API 하나로 통일한다.**
   - 예외 (2026-09-25 결정): Open API에 없는 **선수 능력치(OVR)와 시세**는 공식 **FC온라인 데이터센터**(fconline.nexon.com)에서 가져온다. 조건: **개인용**, 카드에 뜨는 위험 선수 2명만 그 순간에 조회, 초당 1회 이하, 12시간 캐시, DB 전체 수집 없음, 재배포 없음. `robots.txt`가 해당 페이지를 막지 않는 것을 확인했다. 제3자 사이트 중 FCBeta는 AI 크롤러를 명시적으로 막고 있어 쓰지 않는다.
5. **Spotify나 YouTube 내장**: 무거워진다. 대신 **이미 실행 중인 Spotify, 브라우저, 멜론 등을 Windows 미디어 세션으로 제어**하는 방식이 훨씬 가볍고 쓸모 있다 (9장).

**기획을 이렇게 바꾸길 권한다**

6. **100경기를 기본값으로 쓰지 않는다.** 처음 만나는 상대의 100경기 분석은 API 호출 약 103회다. 킥오프 전에 끝나지 않는다. **기본은 최근 30경기**, 백그라운드에서 50경기까지 확장하고, 100경기는 상세 페이지에서 요청할 때만 조회한다.
7. **부드러운 히트맵보다 구역 격자가 낫다.** 30경기면 골이 대략 60개 안팎이다. 이 정도 표본으로 그린 히트맵은 우연한 뭉침을 패턴처럼 보이게 만든다. 요약 화면에는 **6~9개 구역의 비율(숫자)**을 쓰고, 히트맵은 상세 페이지의 점 분포(shot map)로만 보여준다.
8. **지표 40개를 나열하지 않는다.** 요약 화면에 들어갈 기준은 "평균적인 유저보다 **뚜렷하게** 다른가"다 (6.1 특이점 엔진).
9. **FC온라인 실행 시 음악 자동 재생은 기본값 OFF.** 대부분의 사용자는 원하지 않는다. "마지막 플레이리스트 준비"까지만 하고, 재생은 미디어 키 한 번으로 한다.
10. **.NET 8은 쓰지 않는다.** .NET 8 LTS 지원은 **2026년 11월에 끝난다.** 지금 시작한다면 **.NET 10 LTS**(2028년 11월까지 지원)가 맞다.

## 6. 상대 분석 기능 아이디어

### 6.1 특이점 엔진 (가장 중요)

모든 지표를 **기준선**과 비교하고, 차이가 큰 것만 요약 화면에 올린다.

- **기준선 만들기**: 내가 만난 상대 전체, 또는 `match` 엔드포인트로 모은 표본의 분포. 쓰다 보면 로컬 DB에 저절로 쌓인다.
- **점수 계산**: `lift = 상대 비율 / 기준 비율`. 표본이 작으면 베이지안 보정(기준선 쪽으로 당김)을 한다.
  - 예: 감아차기 골 10개 중 5개(50%)는 가짜 신호일 수 있다. 60개 중 23개(38%)는 진짜 신호다.
- **표시 조건**: 보정 후 lift ≥ 1.4, 그리고 표본 n ≥ 최소값일 때만 태그를 띄운다.
- **근거 등급을 반드시 함께 표시한다**:
  - `[직접]`: API 필드 그대로 (컨트롤러, 몰수패 등)
  - `[계산]`: 필드를 집계한 값 (감아차기 골 비율)
  - `[추정]`: 패턴에서 해석한 값 (컷백형, 역습형)

### 6.2 득점 루트 분석

- **득점 방식**: `type` 분포 (감아차기, 일반, 헤더, 낮은 슛, 발리 ...)
- **득점 위치**: 경기장을 아래처럼 나눈다.
  ```
  [좌 중거리] [중앙 중거리] [우 중거리]
  [박스 좌측] [박스 중앙]   [박스 우측]
          [6야드 박스 / 골문 앞]
  ```
  폭 방향은 5개 레인(좌 측면, 좌 하프스페이스, 중앙, 우 하프스페이스, 우 측면)으로 나눠 "우측 하프스페이스 감아차기" 같은 문장을 만든다.
- **도움 벡터 분석** [추정]: 도움 좌표에서 슈팅 좌표로 가는 방향으로 패턴을 분류한다.
  - 엔드라인 근처 측면 → 박스 중앙, 짧은 거리: **컷백형 추정**
  - 측면 깊은 곳 → 박스 안 헤더: **크로스형**
  - 중앙 2선 → 박스 안, 전진 방향: **스루패스 침투형** (경기 합계의 `throughPassTry` 비율과 함께 볼 때 신뢰도 상승)
  - 도움 없는 박스 밖 골: **개인 중거리형**
- **득점자 의존도**: "호날두 득점 비중 42%"
- **득점 조합**: 도움 선수 → 득점 선수 쌍 상위 3개

### 6.3 약점 분석 (실점 패턴)

`match-detail`에는 **양쪽 유저 데이터가 모두** 있다. 그래서 상대의 최근 경기에서 **상대 쪽 유저의 슈팅 = 이 상대가 허용한 슈팅**을 그대로 얻을 수 있다. 추가 호출이 전혀 필요 없다.

- "헤더 실점 비율 29% (평균 14%)", "박스 밖 실점 많음", "후반 막판 실점 집중"
- 전적 사이트가 거의 보여주지 않는 정보다. **킥오프 전 실제 전략을 바꿀 수 있는 유일한 정보**라 가치가 가장 높다.

### 6.4 성향 요약 태그 (예시와 계산 방식)

| 태그 | 근거 | 등급 |
|---|---|---|
| 중앙 박스 침투형 | 박스 중앙 골 비율 lift | 계산 |
| 감아차기 선호 | type=2 골 비율 lift | 계산 |
| 중거리 선호 | 박스 밖 슈팅 비율 lift | 계산 |
| 헤더 의존 | 헤더 골 비율 + 크로스형 도움 | 계산 |
| 원맨팀 | 1명 득점 비중 ≥ 40% | 계산 |
| 점유형 | 점유율 평균 ≥ 55% + 숏패스 비율 높음 | 추정 |
| 속공형 | 점유율 낮은데 슈팅 수 평균 이상, 스루패스 비율 높음 | 추정 |
| 막판 강자 | 75분 이후 득점 비율 lift | 계산 |
| 멘탈 약함 | 선제 실점 시 승률 낮음, 몰수패 비율 | 계산 |
| 퍼즈 많음 | `systemPause` 평균 | 직접 |
| 거친 수비 | 파울, 카드, 태클 시도 lift | 계산 |

### 6.5 선수 위험도 (선수별 위협 카드)

- **위협 점수** = 슈팅 관여(슈팅 + 도움)와 득점을 경기 수로 나눈 값. 출전 경기 수로 가중한다.
- `ranker-stats`의 같은 선수·같은 포지션 평균과 비교: "이 상대의 호날두는 랭커 평균보다 경기당 골이 1.6배"
- 강화 등급(`spGrade`)도 함께 표시한다.
- 요약 화면에는 **위험 선수 2명**만 보여준다.

### 6.6 포메이션 추정 [추정]

- 선발 선수의 `spPosition`(교체 선수 제외)을 수비·미드·공격 줄로 묶어 "4-2-3-1 계열"처럼 표시한다.
- 경기마다 추정하고 최빈값을 보여준다. 포메이션을 자주 바꾸면 "포메이션 변동 큼"으로 표시한다.
- 한계: 경기 중 포메이션을 바꾸거나 포지션을 바꿔 쓰면 알 수 없다. UI에 "추정"이라고 적는다.

## 7. 내 플레이 분석 기능 아이디어

내 경기는 조회 비용이 가장 싸다 (한 번 받으면 영구 캐시). 그리고 **내 경기 기록에서 만난 모든 상대의 `ouid`가 공짜로 쌓인다.**

1. **나의 실점 루트 리포트**: 어떤 방식과 위치로 먹히는지, 기준선 대비로 보여준다. "나는 헤더 실점이 평균의 1.8배".
2. **상성 경보**: 나의 실점 패턴 × 상대의 득점 패턴. 둘이 겹치면 킥오프 전에 경고한다. "⚠ 상대 헤더 득점 ↑ × 내 헤더 실점 ↑". **이 프로그램만 줄 수 있는 정보다.**
3. **틸트(멘탈 흔들림) 감지**: 연패 수, 세션 경기 수, 시간대별 승률을 본다. "3연패 뒤 네 번째 경기 승률 31%" → 트레이 알림으로 휴식을 권한다.
4. **내 선수 효율**: 선수별 골, 슈팅 대비 골 비율, 평점 추이. 교체·판매 판단을 돕는다.
5. **결정력 vs 운**: xG(기대 득점) 모델이 생기면 "이번 주는 결정력이 나빴다"와 "기회를 못 만들었다"를 구분할 수 있다 (아이디어 11번).
6. **컨트롤러별, 포메이션별 승률** (포메이션은 추정값).
7. **세션 요약**: 오늘 몇 승 몇 패, 득실, 가장 잘한 선수.

## 8. 경기 전 / 경기 중 / 경기 후 기능

### 8.1 경기 전 (핵심, 3~5초 안에 읽기)

**요약 카드 제안** (사용자 예시를 수정한 것):

```
┌──────────────────────────────────────┐
│ FC고인물123   ⌨ 키보드   🔁 재대결 1승2패 │
│ 최고등급 챔피언스 · 최근30 18-5-7 (60%)  │
├──────────────────────────────────────┤
│ ⚠ 주의                                │
│ 1 감아차기 골 38% (평균 22%) · 우측 HS   │
│ 2 호날두 의존 42% · 굴리트→호날두 9회    │
│ 3 75분 이후 득점 31%                    │
│ 🎯 약점: 헤더 실점 29% (평균 14%)        │
│ 📝 "스루 남발, 지면 탈주"               │
└──────────────────────────────────────┘
```

사용자 예시와 다른 점과 그 이유:

- **평균 점유율, 평균 득점 같은 숫자를 뺐다.** 경기 전에 봐도 할 수 있는 행동이 없다. 상세 페이지로 옮긴다.
- **"주의 3개 + 약점 1개 + 메모"라는 고정 틀.** 읽는 순서가 항상 같아야 3초 안에 읽힌다.
- 재대결 정보와 메모를 **맨 위**에 둔다. 한 번 만난 상대라면 가장 가치 있는 정보다.
- 결과를 **점진적으로 표시**한다. 캐시된 정보 → 최근 10경기 → 30경기 순서로 카드를 갱신하고, 표본 수를 작게 표기한다.

### 8.2 경기 중

- **기본: 아무것도 표시하지 않는다.**
- 선택 기능: 단축키를 **누르고 있는 동안만** 요약 카드를 보여준다 (하프타임, 일시정지 때).
- 음악 자동 볼륨 조절 (9장).

### 8.3 경기 후

- 경기 기록이 API에 올라오면(짧은 간격으로 몇 번만 확인) **경기 리포트**를 트레이 알림으로 띄운다.
  - 결과, 득점 루트, 이번 실점이 내 평소 약점 패턴과 같았는지
  - 상대가 예측(요약 카드)대로 플레이했는지 → "예측 적중률"로 분석 품질을 검증하는 데이터가 된다
- **원클릭 메모 태그**: `스루 많음` `헤더 많음` `탈주` `매너 좋음` `매너 나쁨` `강함` `다시 만나기 싫음`. 텍스트 입력보다 10배 빠르다.
- OCR로 인식한 닉네임과 API의 실제 상대를 대조해 **OCR 오인식 교정 데이터**로 저장한다 (아이디어 20번).

## 9. 음악 및 편의 기능

### 9.1 권장 설계: "플레이어"가 아니라 "미디어 컨트롤러"를 먼저 만든다

- Windows에는 `GlobalSystemMediaTransportControlsSessionManager` API가 있다. **이미 실행 중인 Spotify, 브라우저의 YouTube, 멜론 등**의 곡 정보를 읽고 재생/정지/다음 곡을 제어할 수 있다.
- 웹뷰를 넣지 않고도 "Spotify 연동"이 된다. 코드도 수십 줄이면 된다.
- **v0.5에서 이 컨트롤러를 먼저 넣고**, 로컬 파일 플레이어는 여전히 필요하다고 느낄 때 v1.0에 넣는다.

### 9.2 로컬 플레이어 (v1.0)

- `Windows.Media.Playback.MediaPlayer`를 쓴다. Windows 내장 코덱으로 MP3, FLAC, WAV, M4A(AAC)를 재생한다. **외부 라이브러리가 필요 없다.**
- Windows 미디어 키, 볼륨 팝업의 곡 정보 표시가 자동으로 연동된다.
- 라이브러리는 폴더 경로 + 파일 목록만 SQLite에 저장하고, 앨범 아트는 필요할 때만 읽는다.
- 셔플, 반복, 플레이리스트(M3U 가져오기와 내보내기)

### 9.3 FC온라인 상태 연동

| 요청 | 권장 방식 | 이유 |
|---|---|---|
| FC온라인 실행 → 음악 자동 재생 | 기본 OFF, 옵션 제공 | 원치 않는 소리는 불쾌하다 |
| 경기 시작 → 볼륨 감소 | 게임 창 포커스와 경기 상태 추정(20장)으로 **덕킹** | 경기 시작의 확실한 신호가 없음 |
| 경기 종료 → 볼륨 복구 | 같은 방식 + API로 새 경기 확인 시 확정 | |
| 대안 | Windows 볼륨 믹서의 **앱별 볼륨**을 조절 (게임 소리는 건드리지 않음) | 게임 쪽은 절대 건드리지 않는다 |

### 9.4 글로벌 단축키 (기본값 예시, 모두 변경 가능)

| 단축키 | 동작 |
|---|---|
| `Ctrl+Alt+F` | 지금 화면에서 상대 닉네임 OCR → 검색 |
| `Ctrl+Alt+S` | 수동 검색창 열기 (마지막 OCR 결과가 미리 입력됨) |
| `Ctrl+Alt+Space` (누르고 있기) | 요약 카드 살짝 보기 |
| `Ctrl+Alt+M` | 방금 경기 상대에게 메모/태그 |
| `Ctrl+Alt+P` / `←` / `→` | 음악 재생·정지 / 이전 / 다음 |

- **`RegisterHotKey` API만 쓴다.** 저수준 키보드 훅(`WH_KEYBOARD_LL`)은 쓰지 않는다. 키로거처럼 보이고, 게임 보안 프로그램이 문제 삼을 수 있다.
- 게임 조작 키와 겹치지 않는 조합만 허용하고, 등록에 실패하면 알림을 띄운다.

## 10. 다른 전적검색 사이트와 차별화할 방법

FC.GG, 공식 데이터센터, 각종 랭킹 사이트는 **"사람이 찾아가서 보는"** 도구다. 이 프로그램은 **"필요한 순간에 찾아오는"** 도구다.

| 차별점 | 웹사이트가 못 하는 이유 |
|---|---|
| 0-클릭 (OCR 자동 인식) | 브라우저는 게임 화면을 못 본다 |
| 나와의 재대결 이력, 메모 | 웹사이트는 "나"가 누군지 모른다 |
| 상성 경보 (내 약점 × 상대 강점) | 두 사람의 기록을 함께 분석해야 한다 |
| 특이점만 보여주기 | 사이트는 "모든 정보"를 보여주는 게 목적이다 |
| 약점(실점 패턴) 분석 | 데이터는 있지만 대부분 안 보여준다 |
| 근거 등급 표시 | 추정을 사실처럼 쓰지 않는다는 신뢰 |
| 킥오프 전 예측 vs 실제 결과 검증 | 사이트는 사용자의 경기 흐름을 모른다 |

**경쟁하지 말아야 할 것**: 랭킹, 커뮤니티. 이미 좋은 서비스가 있다.

**방향 변경 (2026-09-25)**: 시세 "조회"는 여전히 만들지 않지만, **시세 분석과 가성비 찾기**는 두 번째 기둥으로 넣는다.
시세는 유저가 정하므로 "같은 스펙인데 싸게 거래되는 카드"를 찾는 것은 기존 사이트가 주지 않는 정보다.
- 1단계 (구현, `tools/market`): 데이터센터 목록 수집 → 포지션별 가격 영향 분석(능력치·약발·특성·개인기·체형·시즌) → 가격대를 정한 가성비 후보
- 2단계 (구현, `FcHelper.Market` + 트레이 "가성비 찾기"): 앱 안의 선수 DB(SQLite 스냅샷, 최근 3개 보관)와 **자동 갱신**
  - 첫 실행: 전체 수집(약 1,300회 요청, 약 45분 — 포지션마다 코어 능력치를 4개씩 4~5번 나눠 받음, 키·체중·체형 포함). 이후 하루 1번 시세만(약 260회, 약 10분), 나머지 능력치·특성은 이전 스냅샷에서 이어받음
  - 수집 항목이 바뀌면(`MarketGroups.SchemaVersion`) 다음 갱신이 한 번 전체 수집이 됨
  - **새 시즌**: 공식 `meta/seasonid.json`(키 불필요)을 3시간마다 확인해 처음 보는 시즌이 있으면 바로 시세 갱신 + 그 시즌 카드의 능력치·특성 수집
  - 게임 실행 중이면 게임 종료(프로세스 종료 이벤트)까지 미룬다. 갱신 중에도 이전 데이터로 검색된다. 끊기면 이어서 받는다
- 3단계 (엔진 구현, `SquadService`; UI는 `docs/UI_PROMPT.md`로 별도 제작): 
  - **스쿼드 짜기**: 포메이션 13종 + 직접 지정, 예산·급여 한도·허용 강화 단계(강화도 자동 선택)·고정/보유/제외, 모드 4가지(최강·균형·가성비·랭커픽). 빔 서치로 같은 선수(시즌 무관) 중복 없이 3안. 소속 팀컬러를 고르면 11명 모두 그 팀컬러 선수로만 짠다(고정한 칸은 예외)
  - **랭커 가격·급여 분배** (`RankerAllocation`): 공식 랭킹(데이터센터, 20명/페이지) 상위 100명 → 각자 최근 공식경기(Open API 3회/명) 선발 11명·강화 → 오늘 시세로 계산. 스쿼드 시세 10억 미만(교체 중인 팀)은 제외. 역할(ST·CF·CAM·윙·측미·CM·CDM·CB·풀백·GK)별 슬롯당 가격 비중과 급여의 평균·10~90% 범위. 3일 캐시. 스쿼드 짜기는 이 범위(가격 ±30%, 급여 ±1) 안의 카드로만 짠다(그 포지션 칸 수만큼 카드가 없으면 범위 해제)
    - 첫 결과(95팀): 스트라이커 한 칸이 스쿼드 시세의 평균 24%(9~40%), 급여 31. 풀백 4%·급여 27, 골키퍼 3.5%·급여 23. 이전에는 OVR 1당 싼 곳에 돈을 써서 공격수가 가장 싸게 뽑혔다
  - **스쿼드 메이커** (AI + 수동): AI 4안 중 하나를 불러와 칸마다 선수 교체·강화 변경, 빈 스쿼드에서 직접 짜기, 일부만 넣고 "빈 자리 AI로 채우기", 전체 강화 일괄(+5/+8/+10/+11/+13), 포메이션 변경 시 같은 포지션→같은 역할 순으로 선수 유지. 칸마다 대체 선수(더 강하게·더 싸게·랭커 픽, 소속 팀컬러와 남은 예산 안에서)와 이름·시즌·정렬 검색. 합계(시세/예산, 급여/한도, 평균 OVR)와 팀컬러 단계를 바로 계산
  - **강화 상한 +11**: +12/+13은 어떤 팩에서도 나오지 않고 강화로만 만들며 시장에 팔지 않는다(시세표 가격은 실제 매물이 아님). 살 수 있는 강화는 +11까지, +12/+13은 보유 카드에만
  - **강화 팀컬러** (백금빛 +11 · 금빛 +8 · 은빛 +5 · 동빛 +3, 5명/8명 단계, 선발 전원 적용 [추정]): 카드 명단이 아니라 강화 단계로 센다. 종류별 하나만 적용되므로 가장 높은 것만. 스쿼드 짜기는 모두 후보로 넣어 "+11 8명 + 나머지 3명 +8~10" 같은 조합을 스스로 고른다. 랭커 95팀 중 79팀이 +11 8명 이상(백금빛 2단계), 정확히 8명이 25팀으로 가장 많음
  - **거래 없는 매물 제외**: 데이터센터 시세 그래프(365일)에서 최근 30일 변동이 8일 미만이면 사실상 살 수 없는 매물. 카드·강화별로 필요할 때 1번 확인, 3일 캐시
  - **감독모드** (홈 화면 세 번째 메뉴): 공식 감독모드 랭킹 상위 1,000명의 팀컬러 픽률(랭커 수·비율·평균/최고/최저 구단가치), 상위 150명의 최근 감독모드 경기(Open API matchtype 52)로 팀컬러별 포지션 인기 선수, 구단주의 감독모드 최근 100경기 분석(전적·승률·평균 득실, 선수별 경기당 지표, 수비-수미-미드-공미-공격 전술별 전적). fc-info의 같은 화면을 공식 데이터로 재현(킹마카이 100경기 27승 41무 32패·평균 득점 1.60·4-1-4-1-0으로 일치)
  - **관련 특성 팀컬러**: 소속 팀컬러 멤버 카드 24장의 카드 상세에서 특성 팀컬러를 읽고, 2장 이상 나온 것(또는 이름에 클럽명 포함) 중 멤버의 60% 이상이 소속 팀컬러 멤버인 것만. 예: 바이에른 뮌헨 → 바이언 첫번째/두번째 트레블, 뮌헨 뉴 공격 트리오, 19-20~25-26 바이에른 뮌헨, 독일 황금세대, 2021 독일. 1주 캐시
  - **환산 OVR** [추정]: OVR + 시장이 약발·특성·개인기·능력치에 매기는 값을 OVR 단위로 환산(가격 모델 계수 / OVR 기울기)
  - **랭커픽**: 데이터센터 데일리 차트(포지션·강화별 사용 선수, 포메이션 이용률·상대 전적, 팀컬러 이용률 — 차트 페이지의 팀컬러 목록에서 id와 함께 30개, 그중 20개 사용), 12시간 캐시, 랭커 범위 지정
  - **숨은 랭커픽**: 랭커가 쓰는데 같은 스펙 대비 싼 카드
  - **가성비 찾기·숨은 랭커픽 세부 검색** (`CardFilter`): OVR 하한·상한(기본 135, GK 140 = 적응도 +5 + 팀컬러·강화 +8 → 148), 가격, 약발, 급여, 키, 체형, 특성 2개, 능력치 조건 3개, 코어 점수, 이름, 랭커 주요 팀컬러 20개 선수만(기본 켬), 호날두·호나우두·굴리트 제외
  - **코어 능력치** (`docs/CORE_STATS.md`): 포지션별 핵심 능력치와 가중치, CB 뻥스탯(헤더·슬라이딩), 키 구간. 코어 점수 = 가중 평균 − OVR
  - **가격 요인**: 포지션·강화별로 코어 능력치·신특·체형·키·랭커 팀컬러 소속이 시세에 주는 영향(%, OVR 환산, 중간 카드 기준 BP) [추정]. 호날두·호나우두·굴리트는 학습에서 제외
  - **강화 효율**: 단계별 가격·OVR 1당 비용·같은 OVR 최저 대안, "강화 vs 다른 카드 구매"
  - **급여 효율**, **시세 추이·급락 알림**(일자별 가격 이력 35일, 갱신 후 트레이 알림)
  - **내 스쿼드 업그레이드**: 최근 공식경기 선발 11명·강화 → 예산 안 1~2명 교체, 팀컬러 자동 감지(카드 상세의 소속·관계 팀컬러 → 멤버 수로 단계 확인) 후 유지
  - **상대 맞춤**: 상대 약점·위협 → 필요한 유형(헤더·중거리·침투·박스 수비·선방 등) 카드, 상대 추정 포메이션 → 랭커 전적상 유리한 포메이션
  - **팀컬러**: 801개 목록(소속 296 · 특성 500 · 강화 5, 데이터센터 탭별로 받아 분류 — id만으로는 구분 안 됨), 단계별 인원·효과, 멤버(목록 검색 필터), 스쿼드 최적화에 단계 보너스 반영
    - 적용 범위: **소속**(클럽·국가 등) 보너스는 단계를 채우면 **선발 전원**, **특성**(예: "2026 프랑스", "갈락티코 1기") 보너스는 **해당 카드만** — 프랑스 11명 중 2026 프랑스 8명이면 그 8명은 둘 다, 나머지는 프랑스만 (사용자 확인한 게임 규칙). 강화("금빛 물결")는 전원으로 계산 [추정: 공식 설명에 대상 없음]
    - 게임처럼 종류별로 하나만 적용(소속 1 + 특성 1). 자동 감지에서 소속이 여럿 걸리면 가장 강한 것만 켬
    - "전체 능력치 +N"은 OVR +N [직접], 개별 능력치(속력 +2 등)는 포지션 OVR 가중치로 환산 [추정: FIFA 공식 근사, `OvrWeights`]
  - **급여 한도**: Open API에 없음. 공식 스쿼드메이커(fconline.nexon.com/squadmaker) 스크립트에 박힌 값(`Number(t??0)>310`)을 주 1회 읽어 기본값으로 사용, 실패하면 마지막 값(처음엔 310). 직접 입력하면 그 값 우선
  - **판매 수수료**: 공식 계산기(fconline.nexon.com/common/calculator)와 같은 식 — 기본 40%, PC방 30%·TOP CLASS 20%·둘 다 50% 할인, 쿠폰 %는 (100 − 혜택%)까지, 쿠폰 카드당 최대 할인 BP 상한. 내 스쿼드 업그레이드의 판매 대금에 적용
  - 공식 Open API `ranker-stats`(랭커 20경기 평균)는 화면에 보이는 카드에만 호출(키 한도 사용)
  - 확인된 사실: 포메이션 전적의 첫 기록은 선택한 포메이션의 기록(예: 4-2-2-2는 4-2-4에 73승 5무 19패)
- 첫 분석(+8 기준)에서 확인된 것: 양발 +28~110%, 라인 브레이커 +49~189%, 트릭스터 +280~290%(표본 작음), 개인기 5성 ST +120%·윙어 +39%, 같은 OVR에서 속력 +1당 +4~5%(ST·CM·CDM), 가속력 +1당 +4%(윙어·센터백)

  1. **완전 자동**: 게임 창이 앞에 있을 때만 매칭 화면의 작은 영역을 초당 1회 비교 → 일치하면 OCR 1회 (18.1 자동 트리거를 v1.0에서 앞당김)

  - 단축키 모드 구현됨 (실제 게임 검증 전). 완전 자동은 수집한 캡처로 매칭 화면 판별 기준을 정한 뒤 구현한다.

## 16. 프로그램을 가볍게 만드는 설계

현실적인 목표: **대기 중 CPU 0%, 메모리 60~120MB** (WPF 특성상 30MB 이하는 어렵다. 그래도 Electron의 1/3~1/5 수준이다.)

1. **폴링하지 않는다.** 게임 감지는 포그라운드 이벤트 훅, 단축키는 OS 메시지, 타이머는 필요할 때만 만든다.
2. **창은 숨기지 말고 닫는다.** 요약 카드와 상세 페이지는 닫을 때 시각 트리를 해제한다. 트레이 아이콘 하나만 남긴다.
3. **`spid` 메타데이터를 메모리에 올리지 않는다.** SQLite에 적재하고 필요한 ID만 조회한다.
4. **선수 이미지**는 디스크 캐시 + 작은 크기로 디코딩(`DecodePixelWidth`)한다.
5. **GC 설정**: 워크스테이션 GC, `ConcurrentGarbageCollection=false`, 메모리 절약 모드. 배포할 때는 ReadyToRun으로 시작 시간을 줄인다.
6. **분석은 백그라운드 스레드에서 낮은 우선순위로** 돌린다. 게임과 CPU를 다투지 않게 한다.
7. **OCR은 요청할 때 1회**만 한다. 자동 모드에서도 게임 창의 작은 영역만, 초당 1~2회 이하로 본다.
8. **원본 JSON 보관**: 매치 상세 원본을 압축해 저장한다. 분석 알고리즘을 바꿔도 API를 다시 부르지 않고 재분석할 수 있다.
9. **오버레이는 소프트웨어 렌더링 옵션**을 두고, 게임 FPS에 영향이 있는지 실측해서 결정한다.

```
src/
  FcHelper.App          WPF: 트레이, 요약 카드, 상세 페이지, 오버레이, 설정 (UI만)

  FcHelper.Analysis     분석 엔진 (순수 함수: 집계, 구역, 특이점, 추정 태그)

  FcHelper.NexonApi.Tests

[Data] 캐시에 없는 matchId만 추림       ← 재대결 상대는 보통 0~5건
   │
   ▼
[NexonApi] match-detail × N (제한기 경유, 최신 경기부터)
   │           └─ 10건마다 부분 결과 → 요약 카드 갱신
   ▼
[Analysis] 분석(algo_version 포함) → [Data] analysis_cache 저장 → [App] 표시
```

### 17.4 API 호출 최소화

1. **매치 상세는 영원히 캐시한다.** 끝난 경기는 바뀌지 않는다. 가장 큰 절약이다.
2. **한 경기 = 두 명의 데이터.** 내 경기를 받으면 상대의 경기 1건도 이미 받은 셈이다. 상대끼리 서로 경기한 기록도 공유된다.
3. **증분 조회**: 목록을 받아 캐시에 없는 ID만 상세 조회한다. 재대결이면 보통 몇 건뿐이다.
4. **최신 경기부터, 부분 결과 표시**: 10건이 모이면 먼저 보여준다.
5. **윈도우 단계화**: 기본 30경기, 필요할 때 50·100경기.
6. **내 경기는 게임 시작 시 한 번 동기화**하고, 경기 후에는 짧은 간격으로 몇 번만 확인한다.
7. **호출 제한기**: 토큰 버킷(초당·일일 한도는 설정값), 429 응답이면 지수 백오프, 일일 사용량을 트레이에 표시한다.
8. **메타데이터는 인증 없는 정적 파일**이라 Key 한도를 소모하지 않는다 ⚠️. 주 1회만 갱신한다.

## 18. 부가 설계 상세

### 18.1 OCR 자동 상대 인식 (질문 20, 21)

**전제 조건**: 게임을 **테두리 없는 창 모드**로 실행한다. 전체 화면 전용 모드에서는 캡처가 검게 나오거나, 오버레이가 뜰 때 게임이 최소화될 수 있다.

**인식 흐름**
1. **보정 마법사 (최초 1회)**: 매칭 화면에서 단축키를 누르고 닉네임 영역을 드래그한다. 좌표는 게임 창 크기 대비 비율로 저장한다 (해상도가 바뀌어도 유지). 현재 등급 영역도 선택할 수 있다.
2. **캡처**: `Windows.Graphics.Capture`로 게임 창의 한 프레임만 가져와 ROI만 잘라낸다. 캡처 이미지는 저장하지 않고 메모리에서 바로 버린다.
3. **전처리**: 3배 확대 → 흑백 → 대비 강화 → 이진화. 배경색에 따라 반전할지를 자동으로 판단한다.
4. **OCR**: `Windows.Media.Ocr`로 한국어·영어 두 번 실행해 신뢰도가 높은 쪽을 쓴다.
5. **후보 생성**: 혼동 문자 조합을 최대 3~5개 만든다. OCR 교정 사전을 먼저 적용한다.
6. **검증**: `id` API로 존재하는 닉네임인지 확인한다. 이렇게 하면 **API가 OCR 검증기 역할을 한다.**
7. **실패 시**: 수동 검색창을 열고 OCR 결과를 미리 입력해 둔다. 사용자는 한두 글자만 고치면 된다.
8. **학습**: 경기 후 API의 실제 상대 닉네임과 OCR 결과를 비교해 교정 사전을 쌓는다.

**자동 트리거 (v1.0)**
- 게임 창이 포커스를 가지고 있을 때만, 매칭 화면 특유의 작은 영역(버튼, 색 띠 등)의 **픽셀 해시를 초당 1회** 비교한다. 일치하면 그때 OCR을 1회 실행한다.
- OCR 엔진을 상시 돌리지 않는다. 픽셀 비교는 비용이 거의 없다.

### 18.2 오버레이 UX (질문 22)

- 창 스타일: `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW` + 항상 위
- **절대 게임의 포커스를 빼앗지 않는다.** 매칭 화면에서 포커스를 뺏기면 준비 버튼이나 조작 입력이 누락될 수 있다. 가장 치명적인 UX 실패다.
- 마우스 클릭은 통과시킨다. 상호작용이 필요하면 단축키로 "조작 모드"를 켠 동안만 받는다.
- 위치: 화면 가장자리 한쪽에 고정하고 사용자가 정한다. 투명도는 조절할 수 있게 한다.
- 표시 시간: 인식 후 N초, 또는 게임 화면이 바뀌면(자동 트리거 신호) 자동으로 사라진다.
- 녹화·방송 제외 옵션 (아이디어 28번)

### 18.3 시스템 트레이 UX (질문 23)

- 아이콘 상태: 회색(게임 미실행) / 초록(게임 실행 중, 대기) / 파랑(조회 중) / 주황(API 한도 근접)
- 좌클릭: 마지막 상대의 요약 카드
- 우클릭 메뉴: 상대 검색, 최근 상대 5명, 내 분석, 음악 컨트롤, 설정, 종료
- 툴팁: 오늘 전적, 현재 재생 중인 곡
- 알림: 경기 후 리포트, 틸트 경고. 알림 빈도는 적게 유지한다.

### 18.4 시작과 종료 흐름 (질문 26)

```
Windows 로그인
  └ (옵션) 시작 프로그램으로 트레이에 조용히 시작 ─ 네트워크 사용 안 함
      ├ 설정 로드, DB 열기(WAL), 단축키 등록, 포그라운드 훅 등록
      │
  FC온라인 실행 감지
      ├ 아이콘 초록색
      ├ 내 최근 경기 동기화 (증분, 백그라운드) → 재대결 DB 갱신
      └ (옵션) 음악 플레이리스트 준비
      │
  매칭 → OCR/수동 검색 → 요약 카드 → 킥오프 시 자동으로 숨김
      │
  경기 종료 추정 → 새 경기가 올라왔는지 짧게 몇 번 확인 → 경기 리포트 알림 → 메모 태그
      │
  FC온라인 종료
      ├ 캐시 정리(선수 이미지 LRU), 음악 일시정지(옵션)
      └ 아이콘 회색, 메모리 반환
      │
  프로그램 종료: 훅·단축키 해제, WAL 체크포인트
```

게임 실행 파일 이름은 처음 실행할 때 창 제목으로 자동 감지하고, 설정에서 고칠 수 있게 한다 (하드코딩하지 않는다).

### 18.5 최근 경기와 장기 경기 나누어 보여주기 (질문 15, 16)

- **요약 카드 = 최근 30경기**, 단 **최근 10경기에 가중치**를 더 준다 (지수 감쇠).
- 상세 페이지: 10 / 30 / 50 / 100 탭 + 기간 그래프
- **스타일 변화 감지**: 최근 10경기와 이전 40경기의 분포(슈팅 종류, 구역, 주력 선수)를 비교한다. 차이가 크면 "⚡ 최근 스타일 변화: 스쿼드 교체 (선수 5명 변경)"을 표시하고, 오래된 데이터는 요약에서 뺀다.
- **패치 감지**: 사용자가 업데이트 날짜를 등록하거나, 모든 상대에게서 동시에 분포가 바뀌는 날짜를 찾는다 (메타 변화).

## 19. 개인정보와 약관 측면에서 주의할 부분 (질문 27)

1. **NEXON Open API 약관**: 결과 데이터를 약관이 허용하는 범위를 넘어 복제·저장·가공·배포하거나 제3자에게 다시 제공하는 것을 금지한다. 애플리케이션 안에 **NEXON Open API 출처 표기**가 필요하다.
   - 개인 PC의 로컬 캐시는 문제가 될 가능성이 낮아 보인다. 하지만 **배포를 고려하는 순간 약관 전문을 다시 읽어야 한다.** 캐시 보관 기간, 공유 기능, 서비스 단계 Key 심사가 달라질 수 있다.
2. **API Key 보안**: 이 저장소는 GitHub에 있다. **Key를 절대 커밋하지 않는다.** 설정 화면에서 입력받아 DPAPI로 암호화해 `%LOCALAPPDATA%`에 저장한다. 나중에 배포하더라도 Key를 실행 파일에 넣지 않는다 (사용자별 Key 입력 또는 서버 중계).
3. **게임 운영정책**: 이 프로그램은 메모리 접근, 인젝션, 입력 자동화, 저수준 키보드 훅을 쓰지 않는다. 그래서 위험이 매우 낮은 구조다. 하지만 "제3자 프로그램 허용 여부"는 넥슨만 판단할 수 있다. **배포 전에는 고객센터에 문의**하는 것을 권한다. 개인 사용 단계에서도 게임 보안 프로그램이 오버레이나 캡처를 막는 경우가 있는지 실제로 확인한다.
4. **다른 유저의 개인정보**: 닉네임과 경기 기록은 공개 정보다. 하지만 **"탈주", "매너 나쁨" 같은 메모는 특정인에 대한 평가**다.
   - 로컬에만 저장한다.
   - 배포판에 메모 공유나 블랙리스트 공유 기능을 넣으면 명예훼손과 개인정보 문제가 생길 수 있다. 넣지 않는 것을 권한다.
5. **화면 캡처**: 캡처 이미지는 디스크에 저장하지 않는다. 디버그용 저장은 옵션으로 두고 기본값은 OFF.
6. **스크래핑하지 않는다**: 공식 홈페이지와 전적 사이트의 자동 수집은 해당 사이트 약관 위반 소지가 있다. 공식 API로 충분하다.
7. **거래 기록(`user/trade`)**: 다른 유저의 거래 기록을 분석하는 기능은 넣지 않는다. 기술적으로 가능하더라도 "사람이 직접 보는 수준"을 넘는 감시 기능이다.

## 20. 경기 상태 감지와 음악 연동 (질문 24)

메모리를 읽지 않으면 "지금 경기 중"이라는 확실한 신호가 없다. 그래서 여러 약한 신호를 조합한다.

| 신호 | 비용 | 신뢰도 |
|---|---|---|
| 게임 프로세스 실행 여부 | 없음 (이벤트) | 높음 |
| 게임 창 포커스 | 없음 (이벤트) | 중간 |
| 매칭 화면 픽셀 해시 (자동 OCR 트리거와 공유) | 매우 낮음 | 중간 → 이후 약 N초 뒤 "경기 중"으로 추정 |
| 사용자 단축키 | 없음 | 높음 |
| API에 새 경기가 올라옴 | 호출 몇 번 | 높음 (경기 종료 확정, 단 지연 있음) |

**음악 연동 규칙 (기본값)**
- 매칭 화면 감지 → 음악 볼륨 70%
- 경기 중으로 추정 → 30% (0이 아님. 오판해도 불쾌하지 않게)
- 경기 종료 확정 또는 게임 창 포커스 이탈 → 100% 복구
- 조절 대상은 **이 프로그램의 플레이어 또는 선택한 앱(Spotify 등)의 앱별 볼륨**만이다. 게임 볼륨은 절대 건드리지 않는다.

## 22. 최종 제안

1. **"전적검색 프로그램"이 아니라 "킥오프 전 개인 비서"로 만든다.** 판단 기준은 하나다. "이 정보를 보고 이번 경기에서 뭔가를 다르게 할 수 있는가?" 없으면 상세 페이지로 보낸다.
2. **처음 만든 기능보다 쌓인 데이터가 더 강한 무기가 된다.** 재대결 이력, 메모, 내 약점, 기준선은 쓸수록 좋아진다. 그래서 **v0.1부터 내 경기 동기화와 영구 캐시**를 넣는다.
3. **추정을 사실처럼 말하지 않는다.** 근거 뱃지와 표본 수가 이 프로그램의 신뢰를 만든다.
4. **자동 인식은 두 번째 단계에서 넣는다.** 수동 검색으로 분석이 쓸 만한지 먼저 검증한다. 분석이 쓸모없으면 OCR은 의미가 없다.
5. **가벼움은 기능 수가 아니라 구조에서 나온다.** 폴링 없음, 영구 캐시, 필요할 때만 OCR, 닫으면 해제.
6. **음악은 "제어"부터.** 이미 쓰는 앱을 제어하는 쪽이 자체 플레이어보다 가치가 높고 가볍다.

### 바로 다음 단계
1. NEXON Open API에서 개발 단계 앱 등록 → Key 발급
2. 3.4의 확인 필요 항목 실측 (호출 한도, 기록 반영 지연, 좌표 방향, 슈팅 종류 코드)
3. `docs/samples/`에 실제 JSON 저장 → 분석 엔진의 테스트 데이터로 사용
4. .NET 10 WPF 솔루션 뼈대 생성 (17.1 구조)
5. v0.1 구현 시작
