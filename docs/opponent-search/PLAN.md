# 구단주 검색 강화 — 작업 계획

사용자가 2026-09-26 승인했다. 원래 번호 1~21 가운데 **7(경기 목록)과 8(맞춤 대응)은 뺐다.** 나머지를 모두 만든다.
진행 상황은 `PROGRESS.md`에 적는다. 공통 규칙은 저장소 루트의 `AGENTS.md`를 따른다.

## 지금 상태 (시작점)

- **창:** `src/FcHelper.App/SearchWindow.xaml(.cs)` (폭 약 440, 세로로 긴 카드)
  - 처음 열면 닉네임 입력칸과 [검색]만 있다.
  - 검색하면 보고서(`ReportView.cs`)가 나온다.
- **보고서 내용:**
  - 닉네임, Lv, 컨트롤러, 이전 닉네임, 재대결 전적
  - 등급 + 최근 N경기 승무패
  - 평균 득점·실점·점유율, 한 줄 요약
  - 주의·약점·상성, 시그니처 골, 위험 선수 2명, 특징, 메모와 태그
  - 상세 분석(접기): 득점·실점 방식과 위치, 패스 구성, 선수, 득점 조합, 기타 수치
- **흐름:** `FcHelperService.LookupAsync(nickname)`
  1. ouid 확인
  2. DB에 캐시된 경기로 먼저 보고서를 보여 준다.
  3. Open API로 최근 경기 ID(`Options.MatchWindow`, 기본 30)를 받는다.
  4. 없는 경기 상세만 받아 DB `matches.json`에 저장한다.
  5. `BuildReport` → `UserAnalyzer`로 분석한다.
  6. 위험 선수의 데이터센터 시세를 붙인다.
- **이미 있는 데이터:**
  - `OpponentReport.Level`, `MaxDivisionName`, `RecentDivisionName`, `PreviousNicknames`, `HeadToHead`
  - `UserAnalysis`: Record(Forfeits 포함), 평균들, `Controller` 비율, 득점·실점 유형과 구역, Players, Combos, Signature, FirstGoal
- **경기 원본(MatchDetail)에 있는 것:**
  - `matchDetail`: controller, matchEndType(1·2 = 몰수), possession, averageRating, 카드, 코너, 오프사이드
  - `shoot`: 합계와 유형별
  - `shootDetail`: goalTime, **x, y**, type, result, spId, assistSpId
  - `pass`, `defence`
  - `player[]`: spId, spPosition, spGrade, status(shoot, goal, assist, pass, dribble, intercept, defending, rating …)
  - `matchDate`
- **캐시:** DB에 `users`, `nickname_history`, `max_division`, `matches`(json), `match_side`(ouid·결과·날짜)가 있다.
  - 한 번 받은 경기는 다시 받지 않는다(API 절약).
  - 내 경기는 `SyncMyMatchesAsync`로 받는다.

## 화면 구성 방향

- **검색 전 (첫 화면):** 1번. 최근 검색, 즐겨찾기, 최근 만난 상대, 자동완성.
- **검색 후:** 위에 머리 부분(2번), 아래에 **탭**을 둔다.
  - `요약`: 지금 보고서 카드. 경기 중 단축키로 여는 경우를 위해 지금처럼 가볍게 둔다.
  - `스쿼드`: 3번, 17번
  - `슈팅`: 4번, 16번, 18번
  - `흐름`: 5번, 9번
  - `비교`: 6번, 12번, 13번, 14번, 15번
  - `선수`: 19번
  - `내 전적`: 20번. 내 계정일 때만 보인다.
- **창 크기:** 창은 크기를 바꿀 수 있게 한다. 기본 폭은 지금처럼 두고, `요약`이 아닌 탭을 처음 열 때 폭을 약 760으로 넓힌다. 사용자가 바꾼 크기는 기억한다(설정 파일).
- **분석 경기 수:** 기본 30경기. [더 보기]로 50·100경기까지 늘린다. 늘릴 때마다 경기당 API 1회라는 안내를 붙인다.
- **계산 위치:** 계산은 `FcHelper.Analysis`에 순수 함수로 넣고 테스트한다. UI는 결과만 그린다.

## 순서와 의존

1. OS-00이 가장 먼저다. 탭이 있어야 나머지 작업을 넣을 자리가 생긴다.
2. 그다음 OS-01 → OS-02 → OS-03 → OS-04(1단계), 2단계, 3단계, 4단계 순서로 한다. 같은 단계 안에서는 순서를 바꿔도 된다.
3. 의존 관계:
   - OS-13 → OS-14
   - OS-05의 좌표 확인 결과를 OS-07과 OS-08이 쓴다.
   - OS-11과 OS-16은 비교 탭 틀을 같이 쓴다.
4. 각 단계가 끝나면 사용자에게 보여 주고, 사용자가 "배포해줘"라고 하면 태그를 올린다(v0.7.0, v0.7.1 …).
